# top_flying_wing 厂家 CAN 协议与代码核对（2026-10-29）

内部资料，不作为业务对接协议对外交付。

## 结论与范围

按厂家 `docs/vendor/CAN2.0 扩展帧通讯协议1.2.pdf` 两页正文核对当前工作区源码：已使用命令的发送帧格式、命令字、补零、位置字节序及周期查询间隔符合文件；接收 ID 与文件存在明确差异，不能声称整个收发实现完全遵循该 PDF。

本轮只检查代码和本地主机测试，没有修改运行固件、重烧板卡或发送实物运动命令。

## 帧与命令核对

| 项目 | 厂家文件 | 当前实现 | 判断 |
|---|---|---|---|
| 帧类型 | 扩展帧，标准帧不执行 | `CAN_ID_EXT`、`CAN_RTR_DATA` | 符合 |
| 长度 | 8 字节，无效数据位补 0 | DLC 8，编码先清零全部 8 字节 | 符合 |
| 默认速率 | 500 kbit/s，可按客户配置 | CAN2 APB1=36 MHz，Prescaler=4，BS1=15，BS2=2 | 500 kbit/s，符合默认值 |
| 主控请求 ID | 默认 1，第 2 页操作说明明确 | `WING_CAN_TX_ID=1` | 符合 |
| 控制器应答 ID | 第 2 页 FAQ：应答地址自动 +1，即默认 2 | `WING_CAN_RX_ID=1`，其他 ID 解码返回失败 | 与本 PDF 不一致 |
| 位置量纲与字节序 | mm，高字节在前 | Byte2=`target>>8`，Byte3=`target&0xFF` | 符合 |
| 周期状态查询 | 100 ms 可以，建议至少 50 ms 较稳妥 | 远程运行和避让期间 RD 周期 100 ms | 符合该周期建议 |
| 动作命令 | 应用发送一次，不周期重复 | UP/DN/MO/ST 由状态转换提交，未以 100 ms 周期重复提交动作 | 符合应用层要求；显式新 stop 可重新提交 ST |

波特率复算：`36,000,000 / (4 × (1 + 15 + 2)) = 500,000 bit/s`。代码位置：`app/Core/Src/main.c`、`app/Core/Src/can.c`、`app/Core/User/Src/wing_controller.c:137`。

以下均为主控发送的完整 8 字节，扩展 ID `0x1`：

| 操作 | 数据 HEX | 代码 |
|---|---|---|
| 上升 UP | `55 50 00 00 00 00 00 00` | `WingProtocol_EncodeAction` |
| 下降 DN | `44 4E 00 00 00 00 00 00` | 同上 |
| 停止 ST | `53 54 00 00 00 00 00 00` | 同上 |
| 状态 RD | `52 44 00 00 00 00 00 00` | `WingProtocol_EncodeStatusQuery` |
| 限位 RL | `52 4C 00 00 00 00 00 00` | `WingProtocol_EncodeLimitQuery` |
| 绝对位置 MO，37 mm | `4D 4F 00 25 00 00 00 00` | `WingProtocol_EncodeMoveTo(37)`，与 PDF 示例完全一致 |
| 绝对位置 MO，70 mm | `4D 4F 00 46 00 00 00 00` | `WingProtocol_EncodeMoveTo(70)` |

MO 是绝对目标位置，不能固定发送 MO 20 来表示每次上升 20 mm。现防夹逻辑使用停止确认后的反馈位置，计算 `min(start+20, top_limit)`，并将结果作为 MO 目标；例如 50→70 mm、95→100 mm，符合协议位置语义。PDF 第 2 页还说明 RD 是多台杆的位置平均值，平均值不等于每台杆的独立位置／极限证明。

## 接收解析与 ID 差异

- UP/DN/ST 的 Byte7：0 允许执行、1 拒绝执行，代码一致。
- MO 应答 Byte2/3 仍为 DatH/DatL，Byte7 为 result，代码要求目标回显一致且 result=0；符合第 1 页命令表。
- RD 应答 Byte2/3 为位置、Byte4 为故障、Byte5 为状态（0 停止、1 运动）、Byte7 为 result；代码解析一致，并按文档故障表限制 0..16。
- RL 应答 Byte2/3 为最高限位、Byte4/5 为最低限位；代码解析一致。该行 Byte7 在文件中没有定义为 result，代码未将其强制解释为执行结果，符合表格。
- 接收前校验扩展帧及 DLC 8；CAN 硬件过滤器接收全部 ID，但 `WingProtocol_Decode` 仍仅接受 ID 1，因此 ID 2 即使到达 FIFO 也会被软件丢弃。

仓库 `README.md:33` 自 2026-08-26 的既有提交起，记录量产控制器使用同 ID 请求／应答，称 PDF 的加一规则不适用于该量产控制器。这是项目既有硬件适配记录，并非本轮台架验证结果。

因此有两个不同结论：

1. **若现场驱动器遵循本 PDF：请求发 1、应答收 2；当前接收代码不兼容，会导致有应答也超时。**
2. **若现场驱动器确为 README 所述同 ID 版本：当前 1/1 配置可适用，但需厂家确认或有效原始抓包支持。**

本次及先前分析仪只监听全部 ID，未捕获任何有效帧，所以不能据此验证应答采用 1 还是 2。接收 ID 差异属于应用层过滤问题，不能单独解释 CAN 位填充错误，也不能使全 ID 分析仪看不到已经有效发送的帧。本次不凭 PDF 或 README 单方面改写现场固件的 ID。

## 时序与未覆盖功能

- 普通升降：RD 停止预检→250 ms 静默→RD 再确认→RL→UP/DN→应答→RD 运行确认。
- 显式停止：ST→ST 应答→RD 已停止反馈；防夹继续 RL→MO→RD 监测，到目标后 ST→RD 停止确认。
- 100 ms 周期查询符合 PDF 建议。部分过渡步骤收到应答后立即发送下一命令；代码没有全局 50 ms 发送间隔。PDF 的 50 ms 建议位于周期 RD 查询问题中，没有明确规定所有不同命令都必须间隔 50 ms，因此应作为台架时序兼容验证项，不能直接定性为硬性违规。
- 文件定义 HELLO（`48 45 4C 4C 4F 00 00 00`）和 RS（`52 53 00 00 00 00 00 00`），当前业务未实现这两个入口。文件没有要求每次升降前必须先 HELLO，因此不构成现有动作编码错误。没有 RS 入口意味着当前代码不能提供厂家定义的控制器复位功能；不等于重启 MCU 会复位驱动器。

## 发送完成语义与当前现场问题

`send_frame` 直接将 `HAL_CAN_AddTxMessage(...) == HAL_OK` 返回为成功。HAL_OK 表示帧进入发送邮箱，不表示已取得 CAN 硬件发送成功确认，更不表示电动杆已执行。

CAN 自动重传开启，当前应用没有在控制超时／故障时调用 `HAL_CAN_AbortTxRequest` 清除仍待发的邮箱。此前实板已读到 ST 长期 TXRQ 置位及位填充错误。故“应用只提交一次”和“底层不会持续尝试发送”必须区分；日志中的 `tx` 不能当成发送成功证据。运动命令异常待发、断线恢复后的过期命令处理还需专门验证，此问题不能靠改命令字解决。
